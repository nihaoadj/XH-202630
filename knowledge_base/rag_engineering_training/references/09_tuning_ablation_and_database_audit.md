# 权威参考 09：调优、消融实验与数据库审计

## 调优先问“哪一层失败”

RAG 调优不是不断改 Prompt。若资料缺失，应该补资料；若正确片段没被召回，应该检查解析、切分、Embedding、查询和 Top-K；若片段已进入上下文但回答仍不忠实，才重点检查生成约束和审核。先定位层级，再改一个变量，才能避免把偶然改进误判为有效方案。

## 建议的消融顺序

1. 固定知识库版本和评测问题，建立不加额外优化的基线。
2. 比较切分策略：结构切分、大小、重叠、清洗规则。
3. 比较检索策略：单路稠密、关键词/稠密融合、不同 Top-K、查询改写。
4. 比较精排：不使用 Rerank、不同候选数、不同重排序模型。
5. 比较上下文与生成：上下文数量、引用约束、拒答策略、提示词版本。
6. 汇总准确性、证据命中、忠实度、延迟、成本和失败案例。

每次实验只修改少量明确变量，并记录随机性控制、模型版本、索引版本和时间。若一次同时更换 Embedding、切片和 Prompt，即使结果变好也无法知道真正原因。

## 审计数据模型

可复现的系统至少需要以下关系：

```text
知识库版本 → 文档 → 切片 → 检索证据
实验配置/请求 → Agent 运行 → Agent 步骤 → 生成资源
生成资源 → 审核结果 → Claim → 证据切片
```

数据库中的稳定 ID、内容哈希、版本字段和运行轨迹共同构成审计基础。向量库只保存索引不足以重现实验；必须同时保存资料版本、查询、候选、最终引用和配置。删除或替换资料时，需决定历史审核记录是保留旧版本引用、标记失效，还是重新审核，不能静默覆盖。

## 观测与质量门槛

- 记录索引文档数、切片数、collection 数量和最后重建时间。
- 为每次生成记录检索查询、证据 ID、审核状态、重试次数和耗时。
- 对关键指标设门槛，例如期望证据 Hit@K、引用完整度、幻觉风险、难度匹配和 P95 延迟。
- 指标下降或资料版本变化后，运行回归评测；不要只依赖人工浏览少数回答。

## 项目落地检查

- 当前 SQLite 模型保存知识目录、能力图谱、诊断、Agent 运行、审核和评测结果。
- Chroma collection 可按知识库重建；重建前后应核对稳定切片 ID 与数量。
- 评测结果需由真实运行写入，避免在演示中把预设数字当成系统成绩。
