# 权威参考 01：RAG 架构与知识生命周期

## 核心定义

RAG（Retrieval-Augmented Generation，检索增强生成）在回答时先从外部知识中取回候选证据，再把问题和证据交给生成模型。它把模型的参数化知识与可更新、可追溯的非参数化知识结合起来。RAG 的价值不是“让模型永远正确”，而是让回答能够基于受控资料更新、引用和复查。

原始 RAG 研究将检索器与生成器组合，用外部记忆补充模型知识。工程系统应把它进一步拆为独立责任：资料治理、解析切分、索引、检索、上下文组装、生成、审核和评测。任一环节出错都可能造成错误回答，因此不能只把问题归因于大模型。

## 最小可用链路

```text
资料登记 → 解析清洗 → 切片 → 向量/关键词索引
→ 查询理解 → 候选召回 → 重排序 → 上下文组装
→ 受约束生成 → 引用/审核 → 评测与反馈
```

- **资料登记**：记录来源 URL、许可、版本、适用范围、更新时间和责任人。
- **解析清洗**：保留标题、段落、代码块、表格等结构；删除导航栏、重复页眉、无意义空白等噪声。
- **索引与目录**：向量库负责相似度召回；关系目录负责版本、权限、来源、能力节点和审计关系。
- **回答与审核**：回答中的事实应能映射回稳定的 `document_id`、`chunk_id`，而不是仅记录本地文件名。

## 知识生命周期

1. **采集**：先判断资料是否权威、是否允许使用、是否与目标能力节点相关。
2. **版本化**：内容变化通过内容哈希识别；不要用“数组下标”或临时路径作为长期 ID。
3. **可重建索引**：同一资料重复入库不产生重复切片；删除资料后同时清理目录和向量索引中的失效记录。
4. **可追溯使用**：记录查询、候选证据、最终引用和审核结果，才能解释某次回答为何如此生成。
5. **反馈改进**：将错题、低相关检索、审核失败和真实用户问题转为新的资料、诊断题或评测样例。

## 常见误区与排查

- 只更新 Markdown、未重建索引：检索仍可能返回旧向量。
- 只保存向量、不保存来源目录：回答无法解释，也难以删除或版本回滚。
- 将整个文档一次塞给模型：上下文成本高，噪声会掩盖关键证据。
- 将“检索到资料”误认为“回答有依据”：生成阶段仍需要引用约束和审核。

## 项目落地检查

- `knowledge_base_id` 是隔离边界；不同知识库的检索结果不能混用。
- `document_id`、`chunk_id`、`content_hash` 必须稳定并可回溯。
- SQLite 保存目录、图谱、诊断和审计；Chroma 只承担语义检索。
- 每次资料更新后，核对文档数、切片数、索引数是否一致。
