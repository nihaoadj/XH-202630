# 权威参考 02：文档解析、清洗与 Chunk 切分

## 为什么解析和切分决定检索上限

向量模型只能编码送入它的文本。若 PDF、网页或 Markdown 在解析时丢失标题、代码、表格含义，后续 Embedding 与重排序都无法恢复原意。切分也不是把字符平均截断：切片太大时一个向量混入多个主题；太小时定义、条件和例外被拆散，模型虽召回片段却无法回答完整问题。

LangChain 的文本切分文档建议通用场景从递归切分开始：优先保持段落，再尝试换行、句子或更小单位。结构化文档则应优先按 Markdown 标题、HTML 标签、JSON 对象或代码函数切分，以尽量保持语义边界。

## 处理顺序

1. **识别格式和编码**：区分 Markdown、HTML、PDF、DOCX、CSV、JSON、代码；记录原文件哈希和来源。
2. **保留结构**：标题层级、章节名、页码、表格标题、代码语言可作为元数据，而不是丢弃后只留下纯文本。
3. **清洗噪声**：去掉菜单、广告、页脚、重复版权声明；不要删除具有规范含义的警告、版本条件和例外条款。
4. **按结构初切**：优先在章节、段落或函数边界切分；单元仍超长时再递归切小。
5. **控制重叠**：相邻切片保留少量重叠，以避免定义与例外被切在边界两侧；重叠过大则会增加重复召回和上下文浪费。
6. **生成来源字段**：每个切片至少携带标题、来源路径、文档 ID、切片序号、内容哈希和关联知识点。

## 参数不是固定答案

`chunk_size` 应由资料类型、Embedding 模型的有效上下文、问题粒度和生成上下文预算共同决定。知识问答常从“一个相对完整的小节或若干段落”开始实验，而不是迷信某个数字。`chunk_overlap` 只用于保护边界语义，不是提高召回率的万能手段。

建议使用小型评测集比较不同参数：对每个问题检查期望证据是否进入 Top-K、答案是否完整、上下文是否重复、延迟和 token 是否可接受。若正确资料从未召回，先检查解析和切分；若已召回但回答缺条件，再检查切片是否过碎或上下文组装。

## 失败模式

- **按固定字符硬截断**：可能把“除非/但是/前提条件”留在相邻片段，导致错误结论。
- **标题丢失**：多个相似段落缺少章节名，模型无法区分适用范围。
- **把元数据塞进正文**：会污染语义向量；应以独立元数据保存，并在需要时过滤或展示。
- **只测切片数量**：切片更多不等于检索更好，必须测证据命中和答案忠实度。

## 项目落地检查

- 当前项目为每个片段生成稳定 `chunk_id`、`chunk_index` 和 `content_hash`。
- 文档删除后应同步删除失效切片，避免旧知识继续被检索。
- 对 Markdown 资料，优先让标题和段落边界成为切分依据；代码示例应尽量完整保留。
