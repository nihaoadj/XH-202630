# 权威参考 05：混合检索与 Rerank 重排序

## 为什么采用两阶段检索

双编码器向量检索适合在大集合中快速获得候选；关键词检索擅长函数名、错误码、版本号、标准编号等精确术语。Cross-Encoder 重排序器会同时观察“查询—候选片段”对，通常能给出更细粒度的相关性判断，但计算成本高，不适合对全库逐条打分。

因此常见结构是：先用稠密检索、稀疏检索或两者混合取得较高召回的候选，再对有限候选精排。Rerank 的职责是改善“候选中谁更相关”，不是从未被召回的资料中创造证据。

## 混合检索的适用情形

- 自然语言问法、同义表达多：稠密语义检索通常更有价值。
- 错误码、库名、参数名、版本号：关键词信号不可替代。
- 资料中既有中文解释又有英文 API 名称：混合检索能减少单一表示带来的遗漏。

不同检索器的分数尺度常不可直接相加。基于排名的融合方法（例如 RRF）将多个结果列表按名次合并，可避免把“距离”和“BM25 分数”当成同一种量纲。融合策略、候选数和过滤条件都应进入实验记录。

## Rerank 参数与诊断

需要同时确定两个数：初召回候选数和最终交给模型的上下文数。初召回过小会限制上限；过大则增加精排延迟。最终上下文数过小会遗漏条件，过大则淹没生成模型。应在固定评测集上比较，例如：

```text
仅稠密检索
稠密 + 关键词融合
稠密 + Rerank
混合 + Rerank
```

记录期望证据是否被召回、是否进入最终上下文、回答忠实度、端到端耗时和成本。若正确片段从未进入候选，优先查资料覆盖、切分、查询与 Top-K；若已进入候选但排名靠后，再调 Rerank 或融合。

## 常见错误

- 对全库运行 Cross-Encoder：延迟和成本不可控。
- 把 Rerank 分数当作绝对置信度：它主要适合当前候选集合内排序。
- 用重排序掩盖资料缺失：资料不存在时任何排序都无效。
- 只在一个示例上宣称提升：必须在固定评测集比较平均指标和失败案例。

## 项目落地建议

- 当前项目已具备基础向量检索和 Rerank 教学资料；正式接入混合检索前，应先建立可重复评测集。
- 生成报告中应分别记录召回数、精排候选数、最终引用数和耗时，避免只展示最终回答。
