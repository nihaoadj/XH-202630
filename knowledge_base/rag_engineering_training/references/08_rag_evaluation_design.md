# 权威参考 08：RAG 评测设计与指标解释

## 为什么必须拆层评测

回答写得流畅，不代表检索正确或事实有依据。RAG 至少包含资料、检索、上下文和生成四层；评测应能定位失败发生在哪一层，才能指导改进。LangSmith 的 RAG 评测教程将常见目标区分为回答正确性、回答相关性、对检索文档的忠实度，以及检索结果相对问题的相关性。

## 评测集的最小结构

每个样例至少记录：

- 用户问题与问题类型；
- 关联知识点、难度和知识库版本；
- 期望证据文档或切片；
- 参考答案，或明确的评分量表；
- 是否允许拒答、需要哪些限定条件；
- 实验配置，如切分版本、Embedding、Top-K、是否 Rerank、提示词版本。

优先从真实教学提问、诊断错题、审核失败案例和典型边界条件构建样例。不要只用系统自己生成的“容易题”，否则会与系统偏好同质化，无法暴露真实缺陷。

## 推荐指标

| 层次 | 问题 | 示例指标 |
| --- | --- | --- |
| 资料覆盖 | 知识库是否包含答案所需事实？ | 覆盖率、无资料比例 |
| 检索 | 期望证据是否被召回并排在合理位置？ | Hit@K、MRR、检索相关性 |
| 上下文 | 最终给模型的片段是否足够且不过度噪声？ | 证据覆盖、上下文相关性 |
| 生成 | 回答是否正确、相关、忠实于证据？ | 正确性、忠实度、引用完整度 |
| 工程体验 | 是否可在成本与延迟预算内运行？ | P95 延迟、失败率、token 成本 |

有参考答案时可做离线正确性比较；没有参考答案时仍可评估检索相关性、回答对上下文的忠实度和格式约束。LLM-as-judge 可用于语义判断，但评分提示词、模型版本和抽样人工复核都应记录。

## 实验方法

一次实验只改变一个主要变量，例如切片大小、Top-K、是否使用 Rerank。对每次实验保存配置与逐样例结果，再汇总平均值和失败样例。不要只展示最高分：应解释指标提升是否伴随延迟增加、是否在某类问题上退化。

LangSmith 建议评测包括数据集、目标函数和评估器三部分；其文档也强调在上线前使用人工整理样例进行离线评测，并将线上失败轨迹回流为新样例。

## 项目落地检查

- `contest_eval_cases` 保存题目、期望证据和配置；`contest_eval_results` 保存真实运行结果。
- `/api/evaluation/summary` 只汇总已入库的结果，空数据时应返回空统计，不能伪造比赛指标。
- 当前应优先录入 5–10 个代表性样例，再扩展覆盖不同节点和难度。
