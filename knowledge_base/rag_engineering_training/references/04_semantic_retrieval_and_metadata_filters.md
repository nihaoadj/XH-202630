# 权威参考 04：语义检索、Top-K 与元数据过滤

## 检索问题的本质

检索的目标不是找“看起来最像”的段落，而是在有限延迟和上下文预算内，尽可能找回回答问题所需的证据。应区分三类失败：知识库根本没有资料、资料存在但未被召回、资料被召回却没有进入最终上下文。三者的修复方法完全不同。

语义检索通常把查询文本编码为向量，并在 collection 中做近邻搜索。Chroma 的 Query API 支持基于文本或预先计算的查询向量检索；Query 与 Get 都支持 `where` 元数据过滤，后者可按 ID 或条件取记录而不进行相似度排序。

## 查询构造

原始问题可能含有目标、约束、产品名和多个子问题。工程上可保留原始问题，同时生成有限数量的补充查询，例如“主题 + 薄弱知识点”“错误信息 + 组件名”。补充查询必须可记录、可回放，不能无边界扩张，否则会引入噪声和不可控成本。

对教学系统，人物画像中的薄弱点可作为补充查询词，但不能替代用户当前主题。检索结果应去重，并记录每条证据的查询词、排名、分数和切片 ID，供后续引用与问题排查。

## Top-K 与过滤

- **Top-K 太小**：关键片段可能没有进入候选集，重排序也无法找回。
- **Top-K 太大**：噪声、重复片段和上下文成本增加，生成模型反而更容易偏题。
- **元数据过滤**：用于限制知识库、版本、资料类型、权限或目标人群；过滤应在检索阶段完成，而不是把不该出现的资料交给生成模型后再删除。
- **文档内容过滤**：适合精确术语、错误码或必须出现的关键词，但不应取代语义检索。

Chroma 的过滤值应使用支持的标量类型。若多值标签被序列化为 JSON 字符串，过滤前需明确字段格式；不要假设任意 Python 列表都能直接写入或查询。

## 检索诊断清单

1. 目标资料是否真的已解析、入库并在当前 collection 中？
2. 目标切片的内容是否包含回答所需定义和条件？
3. 查询是否使用了正确知识库 ID、语言和术语？
4. 过滤条件是否意外排除了目标资料？
5. Top-K 是否足以让目标进入候选集？
6. 目标在候选中但排名低时，再考虑 Embedding、混合检索或 Rerank。

## 项目落地检查

- 检索 API 必须传递 `knowledge_base_id`，避免跨知识库召回。
- 返回给生成器的证据应保留 `chunk_id`、来源路径、查询词和排名。
- 空查询和非正 Top-K 应直接拒绝，而不是默默返回不可解释结果。
