# 综合学习模块 06：RAG 评测、消融实验与生产运营

> 本模块将评测集设计、检索与生成指标、消融实验、监控和审计合并讲解。
> 主能力节点：RAG 评测、RAG 调优。适用层级：进阶 RAG。

## 学习目标与阅读路径

学完后应能构建具有来源答案和难例标签的评测集，分层计算检索与生成指标，校准 LLM-as-judge，通过单变量消融定位收益来源，并把离线结果与线上监控、审计记录关联起来。应按“数据集—基线—指标—消融—代价—结论”的顺序完成实验。

## 1. 为什么必须分层评测

RAG 是模块系统。最终答案错误可能源于语料、解析、切片、召回、排序、上下文或生成。只看一个总正确率无法指导改进。

至少分四层：

1. **语料与索引**：资料是否完整、解析是否正确、来源是否可追溯。
2. **检索**：相关证据是否被召回并排在前面。
3. **生成**：答案是否正确、相关、完整、忠于证据。
4. **系统**：延迟、成本、稳定性、权限、版本和反馈变化。

## 2. 评测集字段与覆盖

每条样本至少包含 case_id、query、目标能力节点、期望文档/片段、参考答案、难度和标签。还应覆盖精确术语、缩写、错误码、同义表达、多跳问题、否定条件、版本冲突、无答案、越权资料和恶意文档。

样本来源、标注者、审核状态和版本必须可追溯。

## 3. 检索指标

- **Recall@K**：前 K 个候选是否包含相关证据，回答“正确材料有没有机会进入后续步骤”。
- **Precision@K**：前 K 个候选中相关结果比例，反映噪声。
- **MRR**：第一个相关结果排名的倒数，适合关注首个正确证据。
- **NDCG**：支持多级相关性并考虑位置折损，适合排序比较。

指标必须说明是文档级还是片段级。Chunk 策略变化会改变片段 ID，跨方案比较时可增加语义证据覆盖标注。

## 4. 生成与 Claim 指标

LangSmith 官方教程把 RAG 评测拆成：

- 正确性：回答与参考答案是否一致；
- 相关性：是否回应用户问题；
- 忠实度：是否被检索证据支持；
- 检索相关性：文档是否与问题相关。

RAGAS 提供参考答案不完整时评估上下文和忠实度的思路，但自动指标不是事实裁判，必须用人工样本校准。

Claim 级评测可记录关键 Claim 总数、被支持数、不支持或冲突数和引用准确率。幻觉率必须写清分母，例如：

~~~text
unsupported_claims / all_verifiable_claims
~~~

不能把模型输出的一个 0–1 自评分数直接称为真实幻觉率。

## 5. LLM-as-judge 的可靠性

LLM 评委适合语义相关性、忠实度和风格判断，但受评分提示词、评委模型、位置偏差和输入长度影响。应使用结构化量表，固定评委版本，输出评分理由，对样本做人工复核，并记录失败和不可解析结果。评委失败不能默认满分。

## 6. 消融实验

一次只改变一个因素：

- 无检索 vs 向量检索；
- 不同 chunk_size/overlap；
- 向量 vs BM25 vs 混合；
- 无重排 vs Cross-Encoder；
- 原查询 vs 多查询 vs HyDE；
- 无引用约束 vs Claim 级引用；
- 无审核 vs 审核修订。

每次记录代码提交、知识库版本、Embedding、参数、评测集、生成模型和随机性设置。不要只报告最好结果，应同时展示基线、改进、成本和失败案例。

## 7. 在线监控

线上监控空召回率、低置信查询、检索/重排/生成 P50/P95 延迟、token 成本、审核不通过率、修订次数、引用打开率、用户反馈和重复提问。按知识点、难度和学习者层级分组，避免平均值掩盖薄弱区域。

用户点赞不能直接等于事实正确，它可能偏好流畅表达，必须与证据审核结合。

## 8. 生产审计

一次生成 run 应关联画像版本、查询改写、过滤器、知识库与切片版本、候选与重排、Prompt 模板、生成模型、资源版本、Claim、引用、审核、延迟、错误码和降级状态。

审计数据要脱敏，不能记录明文 API Key 和不必要的隐私内容。

## 9. 比赛结果表达

可信结论要说明固定测试集、基线与改进指标、代价变化，以及所有实验是否使用同一知识库和模型版本。在没有真实样本时，接口返回 sample_count=0，不能制造演示数字。

## 10. 评测集的可执行样例

评测样本不应只有问题和答案。下面结构可以同时评估检索、生成、引用和拒答：

~~~json
{
  "case_id": "rag_eval_001",
  "question": "RRF 是否直接相加不同检索器的原始分数？",
  "reference_answer": "不是。RRF 根据各路排名的倒数进行融合。",
  "relevant_document_ids": ["module_hybrid_rerank"],
  "relevant_chunk_ids": ["chunk_xxx"],
  "required_claims": ["RRF 使用排名而非原始裸分数"],
  "forbidden_claims": ["RRF 保证提高召回率"],
  "answerable": true,
  "difficulty": "medium",
  "tags": ["精确概念", "混合检索", "反误解"],
  "knowledge_base_version": "2.2.0"
}
~~~

无答案样本将 `answerable=false`，并给出期望行为，例如“说明知识库没有相关证据，不得编造”。冲突样本记录多个有效来源和预期冲突说明。多跳样本列出必须共同召回的片段集合。评测集要划分开发集和测试集，调参只看开发集，避免根据测试题反复优化造成指标虚高。

样本来源可以是专家编写、真实失败日志和受控的合成扩展。AI 生成的问题必须由人核对答案、证据和难度，不能让同一个模型既编题又无人工校验地当裁判。

## 11. 检索指标手算

假设某问题有两个相关片段 A、C，系统返回前五名 `[B, A, D, C, E]`。

- `Recall@5 = 2/2 = 1.0`：两个相关片段都被召回。
- `Precision@5 = 2/5 = 0.4`：五个候选中只有两个相关。
- 第一个相关片段排第 2，因此 `Reciprocal Rank = 1/2 = 0.5`。

若二元相关性下计算 DCG@5，A 在第 2、C 在第 4：

~~~text
DCG@5 = 1/log2(2+1) + 1/log2(4+1)
      ≈ 0.6309 + 0.4307
      ≈ 1.0616
~~~

理想排序把 A、C 放在第 1、2：

~~~text
IDCG@5 = 1/log2(1+1) + 1/log2(2+1)
       ≈ 1 + 0.6309
       ≈ 1.6309
NDCG@5 = DCG@5 / IDCG@5 ≈ 0.6509
~~~

Recall 说明“有没有找全”，MRR 强调“第一个正确证据是否足够靠前”，NDCG 评价整个排序质量。不同问题可能有不同数量的相关片段，应先逐样本计算，再汇总均值，并报告样本数和置信区间。

## 12. 生成、引用和拒答指标

根据官方 RAG 评测口径，可以分别评估：回答相对参考答案的 correctness、回答相对用户问题的 relevance、回答相对检索证据的 groundedness，以及检索文档相对问题的 retrieval relevance。这四项不能用一个“综合正确率”代替。

Claim 级统计可定义：

~~~text
claim_support_rate = 有充分证据支持的 Claim 数 / 可验证 Claim 总数
unsupported_claim_rate = 无支持 Claim 数 / 可验证 Claim 总数
citation_precision = 正确支持相邻 Claim 的引用数 / 全部引用数
citation_coverage = 有引用的关键 Claim 数 / 关键 Claim 总数
~~~

对无答案问题还要测正确拒答率和错误拒答率。系统总是拒答可以获得很低幻觉率，却没有帮助；因此幻觉、正确性、帮助性和覆盖率必须共同报告。

## 13. LLM-as-judge 校准流程

LLM 裁判适合语义正确性和忠实性判断，但具有非确定性和偏差。上线前先由两名人工评审独立标注一批样本，解决分歧后形成 gold 标签；再比较裁判与 gold 的一致率、混淆矩阵和不同标签上的错误。

裁判输入明确分隔问题、参考答案、检索证据和候选回答，要求输出结构化标签及简短理由。温度尽量低，固定模型、提示版本和输出 schema。对关键比赛结果，可以重复评审或使用人工复核边界样本。

避免让裁判根据文风给高分：一个流畅回答可能不忠于证据。也避免把参考答案当成唯一允许表述：语义等价但措辞不同应视为正确。涉及精确数字、版本号和引用 ID 的内容优先增加确定性代码规则。

## 14. 单变量消融实验实例

基线设为：递归切片 500/100、单路向量召回 Top-5、无重排、固定生成模型。按顺序建立版本：

| 版本 | 唯一变化 | Recall@5 | NDCG@5 | Groundedness | P95 延迟 | 单次成本 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| V0 | 基线 | 实测 | 实测 | 实测 | 实测 | 实测 |
| V1 | 加关键词融合 | 实测 | 实测 | 实测 | 实测 | 实测 |
| V2 | 在 V1 上加 Rerank | 实测 | 实测 | 实测 | 实测 | 实测 |
| V3 | 只改变 chunk 为 800/100 | 实测 | 实测 | 实测 | 实测 | 实测 |

V3 必须从明确基线改变一个变量，不能同时换 Embedding、Prompt 和数据集。每个实验保存代码提交、知识库版本、模型版本、随机设置和原始逐样本结果。平均分提升时还要检查：是否只改善简单题、是否伤害精确编号题、是否由少数异常样本驱动。

## 15. 线上监控和反馈闭环

离线集无法覆盖真实表达。线上至少记录空召回率、低相关候选率、引用缺失率、审核失败率、正确拒答率抽样、各阶段 P50/P95/P99、token 和模型成本。所有日志通过 `run_id` 关联，但对用户问题和资料内容执行脱敏与访问控制。

用户“点赞/点踩”不是直接真值。点踩可以触发结构化原因：答非所问、事实错误、引用打不开、内容过时、太难或太简单。经审核的失败样本进入回归集，修复后先跑离线实验，再上线观察。这形成“线上失败 → 人工定因 → 评测集扩充 → 修复 → 回归 → 再部署”的闭环。

## 16. 比赛报告模板

一份可信的比赛结果至少回答：

1. 数据来自哪里，多少样本，怎样覆盖 13 个能力节点和难例；
2. 基线系统是什么，改进版本只改变了什么；
3. 检索、生成、引用、拒答、延迟和成本分别是多少；
4. 评测是确定性规则、人工还是 LLM 裁判，如何校准；
5. 哪些案例仍失败，系统如何降级；
6. 是否能从答案追溯到 Claim、chunk、document 和 source URL；
7. 实验如何通过版本号、运行记录和代码提交复现。

不要在没有样本时展示伪造的 95% 正确率，也不要只展示最成功的几个截图。可以诚实报告当前没有真实评测集，同时展示数据库、接口、评测流程和待采集指标，这比无法复现的漂亮数字更可靠。

## 诊断与练习

1. 为 20 条最小评测样本设计字段，至少覆盖精确编号、同义表达、无答案、冲突资料和多跳问题。
2. 给定候选排名和相关性标注，计算 Recall@K、MRR 与 NDCG，并解释三个指标分别反映什么。
3. 设计一次单变量消融：固定语料、模型和问题，只改变切片、融合或重排中的一个因素，同时记录质量、延迟与成本。
4. 验收标准：检索与生成错误分层统计；评测集有版本；裁判提示和模型可复现；`sample_count=0` 时不生成虚假指标；比赛结论同时报告收益和代价。

### 参考答案与评分要点

- 第 1 题至少含 case ID、问题、参考答案、相关文档/片段、是否可回答、难度、标签和知识库版本；五类题型都要有实际样本，不能只写类型名称。
- 第 2 题 Recall 衡量相关证据找全程度，MRR 关注首个相关结果位置，NDCG 评价整个排序并支持分级相关性；公式、排名和分母必须明确。
- 第 3 题必须只改变一个变量，保存基线与逐样本结果，同时报告质量、延迟和成本。多个组件一起变化只能说明整体版本差异，不能归因。
- 建议总分 10 分：数据集设计 3 分，指标计算 3 分，消融实验 3 分，诚实报告 1 分。没有样本却填入指标属于严重错误。
