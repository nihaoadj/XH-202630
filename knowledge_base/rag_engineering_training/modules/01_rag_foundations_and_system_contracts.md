# 综合学习模块 01：RAG 原理、系统边界与工程契约

> 本模块将入门讲解、权威依据、工程实践和学习检测合并在同一份资料中。
> 主能力节点：RAG 基础概念。适用层级：零基础、Python 基础、进阶 RAG。

## 学习目标与阅读路径

学完后应能解释 RAG 与模型参数知识的区别，画出离线入库和在线回答链路，说明检索器、生成器和证据审核各自负责什么，并能按模块定位一次错误回答。零基础学习者先阅读第 1、2、4 节；有开发经验者继续阅读数据契约、故障定位和验收清单。

## 1. RAG 解决的核心矛盾

大语言模型把训练数据中的模式压缩进参数，这种参数化知识便于流畅生成，却很难按业务要求及时更新、精确删除和逐条追溯。RAG 在生成前检索外部知识，把非参数化知识作为当前回答的上下文，主要解决三个问题：

1. **知识时效性**：资料更新时重建索引，不必重新训练基础模型。
2. **领域覆盖**：模型临时使用企业文档、课程资料和项目规范。
3. **证据追溯**：回答关联原文档和片段，支持复核、审核与删除。

RAG 不是事实保证器。资料没有入库、问题与资料表达差异过大、召回结果被噪声淹没，或者生成器忽略证据时，答案仍可能错误。工程上必须把检索质量和生成质量分开测量。

## 2. 从经典 RAG 到模块化流水线

Lewis 等人的 RAG 工作把生成模型与可检索的稠密向量索引结合。论文讨论了两种知识使用方式：

- **RAG-Sequence**：一条输出序列主要依赖同一组检索文档。
- **RAG-Token**：生成不同 token 时允许综合不同文档。

现代应用一般采用模块化流水线：

~~~text
资料治理 → 解析与切片 → Embedding → 向量/关键词索引
用户问题 → 查询处理 → 候选召回 → 融合/重排 → 上下文组装
→ 受约束生成 → Claim/引用审核 → 返回答案与证据 → 反馈和评测
~~~

这种拆分让每一层都能替换和单独评测。例如，检索器可以从纯向量召回升级为混合检索，而不必重写资源生成、审核和数据库模型。

## 3. DPR 提供的稠密检索直觉

Dense Passage Retrieval 使用双编码器分别编码问题和文本片段，得到固定维度向量，再以点积或相似度搜索候选。文档向量可以预先计算，因此大规模检索速度较高。

双编码器的优点是离线可索引、在线检索快；限制是问题和文档在编码阶段没有逐 token 交互，精细相关性通常弱于 Cross-Encoder。由此形成常见两阶段架构：

1. 双编码器或关键词检索快速召回较大的候选集。
2. Cross-Encoder 联合读取“问题—候选文档”对，对较小候选集精排。

不要把向量分数直接解释为正确概率。相似度只表达模型空间中的接近程度，其数值会随 Embedding 模型、归一化方式和距离度量变化。

## 4. 离线索引与在线回答的工程边界

### 4.1 离线侧必须产出的信息

每个文档至少需要：

- 稳定的 `knowledge_base_id`、`document_id` 和版本；
- 来源 URL 或受控文件路径、标题、发布时间和更新时间；
- 内容哈希、解析器版本、许可与适用范围；
- 每个切片的 `chunk_id`、顺序、正文和知识点；
- Embedding 模型名称、维度、归一化与索引配置。

没有这些字段，后续无法回答“为什么召回这段”“更新后哪些向量需要删除”“某条引用是否仍然有效”。

### 4.2 在线侧的最小数据契约

检索器返回的每条候选不应只有文本，还应包含稳定片段 ID、文档 ID、正文、分数、排名、实际查询、知识点和来源。生成器只能把候选当作证据输入；审核器必须访问同一组稳定 ID。若生成器和审核器使用不同证据快照，审核结果不可复现。

## 5. 什么时候需要检索

固定对所有问题都检索并不总是最优。Self-RAG 强调按需检索和自我反思：闲聊、格式转换或只依赖用户刚提供的信息时，外部检索可能增加延迟和噪声；涉及事实、领域规范、版本信息或引用时，应优先检索。

- **必须检索**：事实问答、课程知识、制度条款、需要引用的回答。
- **可能检索**：解释、比较、方案设计。
- **通常不检索**：纯改写、摘要用户刚提交的完整文本、无知识依赖的格式任务。

是否检索的决定也应记录进 Agent trace。

## 6. 回答错误时的定位顺序

1. **语料缺失**：正确资料是否真的存在于知识库？
2. **解析错误**：表格、标题、列表、代码或 PDF 是否被破坏？
3. **切片错误**：答案所需条件是否被分散到多个无关联片段？
4. **召回失败**：相关片段是否进入候选集？检查 Recall@K。
5. **排序失败**：相关片段进入候选但排名太低？检查 MRR/NDCG。
6. **上下文污染**：无关或冲突片段是否挤占上下文？
7. **生成不忠实**：证据正确但模型增加了未被支持的断言？
8. **引用错误**：答案正确但引用指向不支持该结论的片段？

只有定位到具体层，调参才有意义。直接换更大的模型不能修复数据版本、权限或引用错误。

## 7. 项目验收清单

- 可以从回答追溯到 `chunk_id → document_id → source_path`。
- 删除或更新文档后，旧片段不会继续被召回。
- 查询、候选、重排结果、最终引用和审核结果关联到同一 run。
- 检索失败与生成失败使用不同错误码和指标。
- 无证据时明确拒答或降级，不把模型记忆伪装成知识库结论。
- “幻觉率低于某值”的结论来自固定评测集，而不是单次人工感觉。

## 8. 完整案例：把课程资料变成可追溯问答

假设系统要回答“为什么中文资料切片要加入中文标点分隔符”。离线侧先登记 LangChain 官方页面，保存来源 URL、抓取时间、许可状态和版本；解析后保留标题层级与代码块；切片器生成带 `knowledge_base_id`、`document_id`、`chunk_id`、`content_hash` 的片段；Embedding 服务编码片段并写入对应 collection；关系数据库保存文档目录、能力节点和来源信息。

在线侧收到问题后，不能直接把问题交给大模型。系统先确定学习方向所绑定的知识库，再规范化查询并执行检索。候选片段经过过滤、去重和排序后组成证据包，生成器只能依据证据作答。回答中的“默认分隔符可能把中文词语切断”属于可核验 Claim，应绑定到包含该说明的片段；如果没有召回该片段，系统应说明证据不足，而不是靠模型记忆补写。

这条链路至少产生以下可审计记录：

| 阶段 | 关键输入 | 关键输出 | 失败时首先检查 |
| --- | --- | --- | --- |
| 入库 | 原始文件、来源、版本 | 文档记录 | 解析日志、内容哈希 |
| 切片 | 清洗文本、参数 | 稳定片段 | 空片段、断句、重复率 |
| 索引 | 片段、Embedding 版本 | 向量记录 | 维度、collection、写入数 |
| 检索 | 问题、知识库、过滤条件 | 候选与分数 | 查询改写、Top-K、权限 |
| 生成 | 问题、证据包、约束 | 回答与引用 | token 截断、指令遵循 |
| 审核 | 回答、Claim、证据 | 审核状态 | 证据绑定、审核器异常 |

## 9. 推荐的跨模块数据契约

检索输出不应只是一组字符串。最小结构可以表示为：

~~~json
{
  "run_id": "run_20260807_001",
  "knowledge_base_id": "rag_engineering_training",
  "query": "中文文档如何切片",
  "index_version": "2.2.0",
  "candidates": [
    {
      "chunk_id": "chunk_xxx",
      "document_id": "module_ingestion_chunking",
      "content": "……",
      "score": 0.31,
      "rank": 1,
      "source_urls": ["https://docs.langchain.com/..."]
    }
  ]
}
~~~

这里的 `score` 必须同时记录度量方式和方向：有的实现分数越小越相似，有的越大越相似，不能跨模型直接比较裸分数。`index_version` 用于重现实验，`run_id` 用于把候选、生成资源、Claim 和审核结果串联起来。列表字段进入只接受标量的向量库前可以 JSON 编码，但返回业务层时应恢复为列表。

## 10. 是否启用 RAG 的决策树

1. 问题是否依赖组织内部、近期更新或必须引用的事实？若是，应检索。
2. 问题是否只是格式改写、翻译或基于用户已提供文本的摘要？通常不必额外检索。
3. 当前知识库是否覆盖问题领域？若不覆盖，应拒答、切换知识库或提示补充资料。
4. 是否存在强权限边界？必须在检索前施加过滤，不能先召回再让模型“不要泄露”。
5. 检索是否达到最低证据门槛？未达到时进入证据不足分支，不调用自由发挥的生成流程。

## 11. 三类典型失败的逐层定位

**答案流畅但事实错误**：先看被引用片段是否真的支持 Claim。如果片段不相关，是检索或排序问题；片段正确而回答改写了条件，是生成忠实性问题；片段本身过期，则是语料治理问题。

**总是回答“没有资料”**：确认学习方向是否绑定正确 `knowledge_base_id`，集合是否有向量，查询是否被错误过滤，Embedding 是否与索引版本一致，Top-K 是否为正数。不要一开始就提高模型温度。

**引用能打开但答非所问**：引用存在不等于引用正确。应检查 Claim 与证据的蕴含关系，并把“引用覆盖率”和“引用正确率”分开统计。

## 诊断与练习

1. 判断题：“只要接入向量数据库，生成答案就一定可追溯。”回答并解释原因。
2. 画出“资料更新后使新内容可被回答”的完整链路，标出离线步骤和在线步骤。
3. 给出一个“检索正确但回答错误”和一个“检索错误导致回答错误”的案例，说明应分别查看哪些日志字段。
4. 验收标准：能区分参数化知识与外部知识，能说出 RAG 不保证事实正确的至少两个原因，并能描述无证据时的拒答策略。

### 参考答案与评分要点

- 第 1 题为错误。可追溯要求片段保留稳定 ID、文档和来源，回答引用真实绑定到片段；仅有向量库不满足这些条件。指出其中两项得基本分，说明 Claim 级绑定得满分。
- 第 2 题应包含来源登记、解析清洗、切片、Embedding、索引写入、检索、证据组装、生成、引用和审核；能正确划分离线与在线阶段才算完整。
- 第 3 题中，前者应检查候选、Prompt、回答 Claim 和引用；后者应检查查询、过滤、召回排名、分数与索引版本。若只说“换模型”不得分。
- 建议总分 10 分：概念边界 3 分，链路 3 分，故障分层 3 分，无证据策略 1 分。低于 6 分时将 `RAG 基础概念` 保持为 `in_progress`，而不是直接判定掌握。
