## 1. 确定升级方向

**公共知识只检索一次，各类资源补充检索自己的资料；证据统一校验和冻结，Planner 看完整批最终证据做一次规划，每份资源的生成与审核使用同一份“公共＋专属”证据。**

例如，同一批生成“RAG 重排”的讲义、实操指南和测试题：

| 使用者 | 可以看到的证据 |
|---|---|
| Planner | 本批最终保留的全部证据，以及各资源的分配关系 |
| 讲义生成与审核 | 公共证据＋讲义的原理、适用条件资料 |
| 实操生成与审核 | 同一份公共证据＋实操的配置、步骤、验证资料 |
| 测试题生成与审核 | 同一份公共证据＋测试的概念区别、判断条件资料 |

“专属”表示分配用途，不要求证据互斥。一段资料适合两种资源时，可以同时分配，正文只保存一份。分配标签不证明某条事实正确，内容支持关系仍需审核。

本次升级保留现有工作流节点、顺序和领域分层；改动集中于已有检索、规划输入、资源规格及审核证据范围。它需要这些环节配套修改，不能简化为只加查询关键词。

## 2. 当前真实流程与缺点

### 2.1 实施前流程（当前 legacy 模式保留）

```text
用户选择主题、目标知识节点、资源类型
→ diagnose：学情诊断
→ retrieve：规则构造查询，混合检索、重排、来源校验
→ 记录并冻结 Evidence
→ evidence_gate：证据门禁
→ plan：一次统一教学规划
→ generate：构造各资源 ResourceSpec，由专用生成器分别生成
→ 按请求进入现有审核、Claim、修订及发布／草稿路径
```

入口：[检索节点](../../backend/app/agents/shared/retrieval.py)、[证据记录](../../backend/app/agents/shared/recorded_node.py)、[工作流](../../backend/app/agents/resource_workflows/learning_documents/workflow.py)。

### 2.2 实施前核验的五个衔接缺口（T26 已逐项接入）

| 当前实现 | 对本次升级的影响 |
|---|---|
| `RetrieverInput` 不含 `resource_types`；查询仅使用主题、节点或诊断薄弱点 | 同一主题和节点下，资源类型不影响找什么资料 |
| `search_many()` 按 chunk 去重时只保留一个查询归属，再全局截断候选 | 同一片段被多个节点／类型命中的信息会丢失；新增查询也可能挤掉其他查询的候选 |
| Planner 不显式接收选中资源类型，只读前 5 条证据、每条前 160 字 | 可能看不到已检索到的关键条件或专属资料，却要为各类资源提出要求 |
| `build_resource_specs()` 给各资源相同的全量证据 ID | 专用生成器虽然职责不同，收到的证据集合没有按用途区分 |
| 普通审核、Claim 白名单和生成后的来源投影仍以整批证据为输入 | 只收窄生成器输入，会导致生成与审核证据范围不一致 |

源码入口：[检索契约](../../backend/app/models/shared/agent_contracts.py)、[候选合并](../../backend/app/core/retrieval/vector_store.py)、[Planner](../../backend/app/agents/resource_workflows/learning_documents/planner_agent.py)、[规格构造](../../backend/app/agents/resource_workflows/learning_documents/spec_builder.py)、[审核](../../backend/app/agents/resource_workflows/learning_documents/reviewer_agent.py)、[Claim](../../backend/app/agents/resource_workflows/learning_documents/claim_review_agent.py)。

上述为实施前机制缺口；T26 在增强模式分别补齐类型查询、完整归属、有界分配、完整 Planner 输入和按 spec 消费范围。legacy 模式保留原行为。已有混合检索、节点约束、来源版本与 hash 校验、结构化契约和审核仍有作用，程序接入不等于已经测得幻觉率。

### 2.3 可以直接复用的能力

- `ResourceSpec.evidence_ids` 已支持证据子集；其 `node_evidence_map` 必须是该子集中的 ID。
- [生成器基类](../../backend/app/agents/resource_agents/base.py) 已按 spec 选择证据，并拒绝不存在的 ID。
- [测评专审](../../backend/app/agents/resource_workflows/learning_documents/specialized_reviews/assessment_scope.py) 已进一步按题目引用 ID 限定证据。

因此无需建立第二套证据库、多个 Planner 或新的生成工作流。

## 3. 升级后的连续流程

```text
现有请求：主题＋知识节点＋已选资源类型
→ retrieve 内按规则分配公共查询和类型专属查询
→ 现有混合检索与重排，保留多查询归属并有界选材
→ 来源校验，形成公共集 C 与各类型专属集 S
→ 统一冻结 E = C ∪ 所有 S，以及本次分配关系
→ 原证据门禁
→ 一次 Planner：读取完整 E、所选类型、C/S 分配
→ 代码生成 ResourceSpec：每类可用集合 A = C ∪ 本类 S
→ 各类生成、来源记录、审核、Claim 判定和修订均使用对应 A
→ 原发布／草稿／失败处理
```

检索发生在 Planner 之前。专属查询使用请求中已有的资源类型与节点，不依赖尚未生成的大纲、正文或答案。Planner 根据已经拿到的资料规划，不在规划后新增补检索循环。

## 4. 公共与专属查询如何分配

### 4.1 公共查询保留，五类资源各有固定查询重点

公开 [GenerateRequest](../../backend/app/models/learning_documents/schemas.py) 当前最多接受 **2 个目标节点**，本方向不扩大 API 限制。公共查询沿用当前 `_queries()`：主题＋目标节点；没有目标节点时，使用主题及最多 2 个诊断薄弱点。函数内部虽读取输入列表前 3 项，但这是内部兼容上限，不能据此把 3 节点写成当前公开请求能力。相同查询只执行一次。

专属查询使用“主题＋当前节点名称和知识点＋类型用途词”。首版由代码维护以下固定规则，不新增查询规划模型：

| 资源类型 | 专属查询重点 |
|---|---|
| 讲义 | 原理解释、概念关系、适用条件 |
| 实操指南 | 前置条件、操作步骤、验证方法、常见错误 |
| 分阶测试题 | 概念区别、判断条件、适用边界 |
| 复习清单 | 核心要点、易混淆点、常见错误 |
| 案例分析 | 应用情境、决策依据、限制条件 |

使用 [types.py](../../backend/app/models/learning_documents/types.py) 中的中文规范类型名称。没有目标节点的普通请求以主题为专属查询范围，不伪造节点 ID，不扩展学习目标。

增加带默认值的检索输入字段。开关关闭、缺少资源类型、其他共享检索调用，以及含“个性化纠错训练包”的内部请求继续走旧策略；不为 E1 拒绝已有合法调用。

### 4.2 动态预算采用“基础优先，类型轮转”

当前默认查询上限为 6，[RetrievalRequest／Policy](../../backend/app/models/knowledge/knowledge.py) 已允许最多 10。首版为 E1 增加独立的服务端查询上限，推荐默认 10；旧模式仍使用原配置。不是全局把所有调用改成 10 条。

确定分配规则：

1. 先保留原公共查询，设去重后的数量为 B；当前公开请求最多 2 个节点，因此 B 通常不超过 3。内部旧调用仍保留原边界，不从本方案推导新入口能力。
2. 剩余名额按本次请求中资源类型的稳定顺序轮转，每轮每类最多得到一条节点专属查询。
3. 各类型内部轮转目标节点；首个节点按类型序号错开，避免第一轮所有类型都只检索第一个节点。同一“节点＋类型”首版最多生成一条专属查询。
4. 达到查询上限立即停止。需求已经用完则提前结束，不为凑满预算重复检索。
5. 查询规范化、去重后合并全部归属，不丢掉节点或类型。单条查询仍受现有 2,000 字符限制；新增专属查询超长时跳过并记录，不截掉节点名称和知识点。
6. 专属查询未获得额度、查询未命中、候选未通过校验、证据未入选分别记录，不能都描述成“知识库没有资料”。

以下是无重复查询时的分配示例：

| 请求 | 公共查询 | 专属需求 | 实际查询总数 |
|---|---:|---:|---:|
| 1 个节点，实操＋测试题 | 2 | 2 | 4 |
| 1 个节点，五类资源 | 2 | 5 | 7 |
| 2 个节点，实操＋测试题 | 3 | 4 | 7 |
| 2 个节点，五类资源 | 3 | 10 | 最多 10，专属只执行其中 7 条 |

**五类资源都支持专属检索，不等于每次都检索所有节点与类型的组合。** 所有资源仍可使用公共证据；有限预算下，未增强的组合必须可追溯。

若部署将 E1 查询上限设得低于本次公共查询数量，直接停用本次增强并沿用旧策略，不挤掉基础查询。这里只定义首版资源分配规则，不宣称 10 是经实验取得的最优值。

## 5. 如何选证据，避免“查到了却没用上”

### 5.1 补上多归属信息，不复制证据正文

保留现有 `query_node_ids` 的兼容行为，为新策略增加独立的查询归属契约，表达一条查询对应的公共／专属用途、节点和资源类型。去重前后的绑定必须一致。

候选合并时保存“这个 chunk 被哪些查询命中”，一直传到最终分配。不能仅靠 `EvidenceItem.query` 反推全部用途，因为当前 Evidence 只保存一个代表查询。

同一 chunk 仍只生成一个最终 Evidence。多个资源引用相同 Evidence ID，不重复保存正文。节点归属来自查询和现有范围约束，不因命中就声称已证明该片段在语义上完全支持该节点。

### 5.2 保持精排候选上限，增加公平选取

首版采用统一精排候选上限 20，每查询仍使用当前默认 `top_k=3`。为使配额与节点映射一致，**仅在 E1 模式下，将 top_k 明确定义为每查询最多负责送入精排的唯一 chunk 数量**，旧模式保持原来的精排后截取行为。

在现有候选合并处执行以下规则：

1. 先收集本批所有查询的命中及完整归属。按混合分、查询顺序、命中排名和 chunk ID 稳定排序，不因候选池已满而提前停止归属合并。
2. 先为每个公共节点尝试保留一条候选；无目标节点时先保留一条公共主题候选。随后按类型轮转，让每类先获得一次候选选取机会，再轮转各查询填补剩余名额。
3. 新 chunk 入池时，以当前为它取得名额的实际命中查询作为 owner，固定该查询对应的混合分及命中元数据。每个 owner 最多占 top_k 个唯一 chunk，总池不超过 20。已经在池中的 chunk 只合并归属，不重复占名额。
4. 精排使用 owner 查询与 chunk 配对，每个 chunk 只精排一次；按 owner 分组重排并编号 `query_rank=1..k`，其中 k 不超过 top_k。保留当前 `query_rank≤top_k` 校验，不再按另一条最高分 origin 查询重新截断。重排 fallback 同样使用 owner 的混合分，不混用其他命中的分数。
5. 其余命中仅用于节点／类型分配，不伪称它们得到了独立精排评分。来源非法或分数不达标仍按原校验与错误策略处理，名额不豁免质量要求。

这是原候选合并路径的局部策略调整，不是原实现已经具备的能力。例如 4 条查询、top_k=3 时最多送入 12 个唯一候选，无需凑到 20。提前分配名额可能改变重排候选及质量，必须与旧流程对照验收。20 不是所有召回渠道合计只读取 20 条；增加查询仍增加混合检索和 Embedding 成本。

### 5.3 最终公共集 C、专属集 S 与统一池 E

首版保留当前默认 **最多 8 条最终 Evidence、每条最多 1,200 字符**，不随资源数量成倍放大。实际数量由可用结果决定，现有最小数量和分数要求继续生效。

完成来源校验、分数过滤后按以下顺序分配：

1. 公共集 C 优先从公共查询结果中，为每个目标节点选一条有效片段，去重保存；没有目标节点时先保留一条有效公共片段。
2. 某节点公共查询没有合格片段，但专属查询有该节点的合格候选时，可将其中排名最高的一条纳入 C，并记录来源。C 表示共同可使用的节点依据，不要求原文只能讲概念。若没有任何公共候选，仍有合法查询候选时，以最高分片段建立最小 C；不能因此宣称所有节点已有依据。
3. 建立最小 C 后，先按资源类型轮转，从各类型查询的合格候选中为每类尝试一条 S；这一轮不追加公共候选。各类型都得到首次机会后，如果仍有名额，再进入补充轮：每轮先尝试补一条公共候选，再给各类型各一次机会，直到预算用尽或没有候选。
4. 同一片段命中多个类型，可同时属于多个 S；已经在 C 中的片段直接共用，不重复占名额。预算已满也必须补全入选片段的全部类型归属，不能丢掉排在后面的类型。最终仅将入选片段写入 E，C 和所有 S 的引用都必须在 E 内。
5. 分配按确定性分数和稳定次序执行；不得通过降低门槛、放宽知识库范围或凑关键词来填满名额。

以当前合法的 2 个节点、5 种资源为例，2 条公共证据加每类 1 条专属证据最多是 7 条，还有 1 个补充名额。但这只是容量上可容纳，是否找得到合格资料必须实测；重排、去重和来源过滤仍可能留下缺口。

C 和 S 是**可供使用的资料集合**，不是“这些资料一定支持所有待生成事实”的结论。专属集为空时，该资源继续使用 C，记录缺口并交给现有生成和审核处理，不新增“专属证据必须有一条”的发布门禁，不偷偷借用其他资源的 S。

## 6. Planner 读取全部最终证据，仍只规划一次

`PlannerInput` 增加实际选中的资源类型与证据分配信息。新策略启用时：

- 输入全部最终 E 中的 ID、来源、节点归属与完整 `Evidence.excerpt`，删除 `evidence[:5]` 和 `excerpt[:160]` 的二次截断。
- 同时传入 C、各 S、每类可用集合 A 及检索缺口；正文按 E 去重提供一次，不在每类下面重复粘贴。
- 仍输出一份共同学习路径及各已选资源的 `resource_requirements`。现有目标节点硬范围继续生效，不新增每资源独立 Planner。
- Prompt 要求各资源的内容要求依据其 A 提出。代码控制证据分配，Planner 不得重新分配证据或扩大白名单；规则 fallback 同样只为已选类型生成范围内要求，并保留降级标记。
- trace 的 `evidence_refs` 与实际看到的完整 E 一致。

这里的“全部”是最终筛选并冻结的片段，不是所有原始检索候选，也不是来源文档全文。Planner 的自由文本要求仍可能偏离证据，不能仅凭输入了 ID 映射便声称规划已经得到语义证明。

当前网关没有通用输入 token 预检。E1 必须在 Planner 入口增加完整输入长度检查，并在启用配置时核对部署模型窗口与输出预留。默认 8×1,200 最多约 9,600 个证据字符，不等于 9,600 token，画像、Prompt 和结构化包装也要计入。

若完整输入超预算，不得偷偷删证据或再次截成前 5 条；按现有 `require_agent_fallback` 政策处理预算错误，严格模式失败，允许规则规划时明确记为降级、未完成 AI 规划。预算检查是新增的程序检查，不是新增审核模型。

## 7. 按资源分配，并让生成与审核使用同一范围

### 7.1 ResourceSpec 成为每份资源的证据依据

在现有 `build_resource_specs()` 中，为类型 r 设置：

```text
A[r] = 去重后的 C ∪ S[r]
ResourceSpec.evidence_ids = A[r]
ResourceSpec.node_evidence_map = 本次节点映射与 A[r] 的交集
```

ID 顺序按冻结 E 的排序稳定输出。不能把整批 node map 原样塞进子集 spec，也不能把某类型全部证据都标到每一个节点下。

空交集不写成空列表，因为现有 ResourceSpec 会拒绝该值。对已有契约要求节点证据隔离的资源，显式目标节点缺少可用映射时进入现有证据不足／契约错误路径；新策略不能删成空字典后触发测评生成器的 legacy 全量证据回退。无目标请求继续遵守对应资源已有契约，不借 E1 放宽要求。

沿用现有 ResourceSpec 字段和存储列。分配完成后规格不可变，后续修订复用同一 spec，不在返工时静默加证据。

### 7.2 必须同步的消费路径

| 路径 | 确定改动 |
|---|---|
| 专用生成器上下文 | 按 spec 提供 A 及对应 node map；复用基类的子集校验 |
| 正常产物与 fallback 产物 | 来源引用从 A 投影，不能继续从整批 E 取引用 |
| 普通审核 | 按资源的 `resource_spec_id` 找到对应 spec，模型上下文和程序引用白名单都使用 A |
| 结构化测评专审 | 先限定到 A，再沿用现有每题引用子集；不向通用 Claim 重复提交已跳过的结构化测评 |
| 实操等结构校验 | 保留现有确定性检查，同时保证结构化 payload 的证据 ID 属于 A；不把结构通过当成事实已经通过语义审核 |
| Claim 抽取与 Judge | 当前仍使用 Evidence 的抽取输入及服务端白名单限定到 A；Judge 输入和判定白名单也限定到 A |
| 定向修订 | 继续使用原 spec、原 A 和当前资源的修订反馈，不扩展到其他资源的专属证据 |

当前 [source_refs 投影](../../backend/app/core/retrieval/evidence.py) 默认只显示前三条。本方向保留这一展示上限，但输入改成 A；完整白名单以冻结分配与 spec 为准，不能从三条展示引用反推完整审核范围。

这也澄清“审核沿用现有流程”的含义：审核节点和职责不变，但证据输入与校验范围必须改。当前实操分支主要执行确定性结构检查，不能写成每种资源都已有同样的 LLM 事实审核。Claim 仍按请求开关执行，且公开 API 要求普通审核开启、单请求仅一种资源；多资源分配示例不意味着放开多资源 Claim，也不强制开启 Claim。

本方向先于 [E2](E2-claim-extraction-coverage.md) 实施：在当前抽取器仍接收额外 Evidence 时，先将输入范围限制为本资源 A；后续 E2 移除抽取模型的额外 Evidence 输入。两者都实施后，抽取仅看规范正文，Judge 和引用校验继续使用本资源 A，不能重新向抽取器传入 Evidence 正文。不新增遗漏复核。

## 8. 冻结、持久化与旧记录兼容

### 8.1 新增一份明确的分配契约

在现有模型分层中增加版本化的 `evidence_allocation`，至少包含分配版本、所属检索步骤／config hash、C、按类型记录的 S，以及必要的查询归属和缺口信息。ID 必须指向同一次最终冻结集合，类型必须属于本次请求。

新字段显式贯穿 `EvidenceBatch`、`RetrieverOutput`、运行 state／snapshot、Planner／Generator 输入；不要仅把业务分配塞进自由格式日志。普通审核和 Claim 通过资源 spec 获取实际范围，无需各自推断一份分配。

存储使用当前 JSON 与现有 spec 列：

- 检索返回前验证分配，将同一份分配快照写入 trace 的 `retrieval_profile`，通过现有 `complete_step` 与 Evidence 一起持久化。state 中传递同一已验证结果。
- 在 [build_checkpoint_projection](../../backend/app/models/shared/persistence.py) 显式增加分配及必要节点映射投影。当前 checkpoint 是白名单投影，新 state 字段不会自动保存。
- 各资源的最终 A 和 node map 继续写入已有 `ResourceSpecRecord`／SQL 字段，不给 spec 增加重复存储的 C/S 字段。
- checkpoint 只保存 ID、版本和映射，不复制 Evidence 正文；核对当前默认 64 KiB 的 checkpoint 大小限制和序列化兼容。

本次只要求内部记录与离线评测能够追溯分配，不扩展审计页面、公开 API 或事件 payload。不能把“内部已保存”写成“现有前端已展示”。

### 8.2 版本与回滚

为新查询调度、候选选取和证据分配设置策略版本；模板、排序或分配语义改变必须更新版本。在创建 Evidence 前，将有效策略和预算纳入 config hash，查询绑定及最终分配另存确定性指纹。当前 hash 不会自动涵盖全部 rerank 参数，实施时须补齐新策略实际依赖的配置。

增强开关默认关闭。关闭后新执行走旧策略；已保存的 Evidence、spec、hash、判定与已发布资源不改写。

旧记录有 spec 时以其原始 ID 集合为准，未记录 C/S 则标为历史共享／分配未知，不追溯伪造用途。在运行输入快照中记录本次选择的策略版本，并将实际生效版本写入检索 trace；不能仅靠分配字段是否存在来区分新旧模式。新策略分配或 spec 缺失、越界时按现有契约错误处理，不能因字段缺省就冒充旧运行并回退到整批 E。

当前 checkpoint 用于只读回放，不具备完整的检索断点恢复保证。重试可能重新检索，仍沿用当前执行机制；本方案不新增断点恢复，不能把两个检索步骤的证据混为一次冻结结果。

## 9. 可用性和成本的明确边界

- 沿用原知识库、来源、版本及全文 hash 校验。硬校验失败不能因公共或专属标签而被忽略。
- 节点范围检索只有原来允许的 `NO_HIT`／`EVIDENCE_INSUFFICIENT` 才执行整体全局回退；最终选择一批结果，不拼接两批冻结快照。专属组为空不额外触发全局重查。
- 上游异常和部分查询失败继续遵守严格／降级策略；不把“公共查询成功”当成全部检索正常。重排器 fallback 与混合渠道回退也保留原记录方式。
- 不保证增强后所有旧证据或原排名不变。候选名额保留只是给各组进入后续筛选的机会，不保证过阈值、不保证资料一定存在。
- 新增查询会增加 Embedding、混合检索与部分失败的机会；Planner 从最多约 800 个证据字符增加到完整 E，输入成本会增加。按资源缩小生成与审核上下文可能节省 token，但净成本必须实测。
- 不新增查询规划模型、用途分类模型、独立覆盖复核、生成后补检索或人工审批流程。原有修订次数、工作流时限和发布条件继续适用。

这套方案旨在降低“资料与资源要求不匹配”和“跨资源借用依据”的风险，不保证知识库缺资料时仍能生成正确内容，也不把降低成功率包装成降幻觉收益。

## 10. 实施顺序与验收

### 10.1 在当前目录内逐步升级

| 顺序 | 现有模块与必要工作 |

| 1 | `models/knowledge/knowledge.py`、`models/shared/`：查询多归属、版本化分配、默认兼容、state 与持久化契约 |
| 2 | `agents/shared/retrieval.py`：读取类型、确定性分配查询预算；`core/retrieval/vector_store.py` 与 `retriever.py`：保留归属、有界选材、输出 C/S |
| 3 | `planner_agent.py`：完整 E、选中类型、分配关系、输入预检、Prompt 与 fallback 同步 |

API 不直接构造查询或调用模型；共享层不反向依赖资源工作流／业务 Service。无需新增顶层目录、数据库或重命名数据表，使用已有 JSON 存储；实现中仍需核对 DTO、序列化、仓储与旧记录读取。配置变更同步 README、部署文档与 `backend/.env.example`，架构、功能说明按实际变化同步。

以上步骤属于同一完整升级。没有把审核和来源范围同步完成之前，不启用新策略。

### 10.2 必须通过的确定性验收

- 五类单资源及混合请求：C 相同、S 按类型分配，A 正确且允许交集；同一 chunk 只冻结一次。
- 公开请求的 1／2 个节点、多类型、无节点、低预算、重复查询、超长查询：分配稳定、归属不丢失、预算不超额、未执行组合有记录；3 节点请求仍被现有 API 拒绝，内部辅助函数的旧兼容边界单独验证。
- 同一 chunk 被多个节点和类型命中：候选去重、精排与最终去重后仍能解释归属；owner、评分与 query_rank 一致，池满后仍保留重叠归属；不能只测绕过 `search_many()` 的假后端。
- Planner 第 6—8 条以及第 160 字后的证据能进入实际输入；完整 E 只提供一份正文，trace 与实际输入一致；超输入预算显式处理。
- 普通审核、Claim、测评题目、实操 payload 均拒绝使用另一个资源独有的 S；程序白名单与模型输入一致；节点映射空交集不能触发新策略的 legacy 全量回退。
- 正常生成、fallback、修订都使用同一 spec 范围；公开三条来源引用不被误当全部证据。
- 专属无命中、全局回退、部分失败、来源非法、分配损坏、输入超预算按约定处理；不放宽发布条件。
- 旧 spec／快照可读取，新字段不在 checkpoint 丢失；关闭开关不改历史数据，E2 相关行为不被混入本次改动。

```powershell
python scripts/run_tests.py --suite backend-full
```

命令入口与套件见 [README](../../README.md) 和 [tests/suites.json](../../tests/suites.json)。本次实现按 T26 执行共享后端全量及专项回归，实际结果在第12节记录。

固定知识库版本、主题、节点、模型和生成参数，对照旧流程与新流程。包含专属资料齐全、只有概念资料、同义表达、重复片段、多节点五类型、错误／稀缺来源等样本；独立核定资料是否确实支撑内容，不只依赖生产审核器自评。

## 11. 参考与本次结论

[Haystack MultiQueryEmbeddingRetriever 官方文档](https://docs.haystack.deepset.ai/docs/multiqueryembeddingretriever) 展示了多查询召回、去重、相关性排序的成熟做法，也指出多查询的时间成本。本项目复用已有同类能力，增量在于查询预算分配、用途归属和资源证据范围贯通，不引入 Haystack 替换当前框架。

本版按已确认需求，统一采用**五类资源动态检索＋公共／专属证据分配＋完整证据统一规划＋按资源一致审核**。上一版仅实操、仅改后缀及“不需修改审核输入”的范围已经被本版替代。

实施前已完成真实代码路径、预算上限、Planner 截断、证据子集能力、审核与持久化缺口核验；T26 现已完成业务接入，验证见下节。真实检索／生成对照和成本测量尚未执行，不能据此承诺生产可用性或确定降幻觉幅度。
